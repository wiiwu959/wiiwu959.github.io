What is DLL hooking

Many EDRs hook commonly used or otherwise important APIs to monitor behavior, such as reading files, writing to memory, and creating processes. Whenever these APIs are called, the EDR becomes aware of them and checks whether the behavior is suspicious.

How to hook

Inline unhook

Directly modify the contents of the target API in a DLL.

  • Add a JMP/CALL instruction at the beginning of the DLL function to jump to the EDR.
  • The execution flow is therefore: call critical API → DLL API jump → EDR function → jump back to DLL API
    • It first goes to the EDR to perform the monitoring and logging it needs to do, then returns to the original API to complete its intended operation.

This usually happens when a process is created: the EDR injects its own DLL into the process memory and modifies the memory contents of the target DLL.

  • It locates the memory address of the target API and overwrites its beginning with something like a JMP.

How does the EDR know when a process is created? There are several methods:

  • Windows Native API

    • https://learn.microsoft.com/zh-tw/windows-hardware/drivers/ddi/ntddk/nf-ntddk-pssetcreateprocessnotifyroutineex
    • Such as PsSetCreateProcessNotifyRoutineEX, WMI, or user notification hooks

  • AppInit_DLL

    • https://learn.microsoft.com/zh-tw/windows/win32/dlls/secure-boot-and-appinit-dlls

    Allows you to load a custom DLL into the address space of every interactive application, making it easy to intercept system APIs.

  • Kernel driver

    • Intercept or modify APIs at the driver layer, such as ZwCreateProcess, or use ETW (Event Tracing for Windows) for real-time tracing. It can also inject its own DLL/agent directly during the process creation stage.

  • Remote injection mechanism (Remote DLL Injection)

    • Use APIs such as CreateRemoteThread, NtWriteVirtualMemory, and NtCreateThreadEx to inject the EDR’s monitoring DLL into the target process.
    • C/C++ APIs can be used to copy the DLL path into the other process’s memory and create a thread to execute it.

  • Automatically traverse existing running processes

IAT/EAT Hook

  • IAT Hook (Import Address Table): Modify the pointers in the import table so that an API that originally pointed to A.dll points to EDR.dll instead.
  • EAT Hook (Export Address Table): Modify the pointers in the export table to alter the DLL export function.

This does not modify the DLL itself; instead, it modifies the table pointers. A more advanced approach is to hook the kernel layer or syscalls, but that is outside the scope of DLLs here.

What is kernel32.dll

It is a commonly used DLL in Windows that provides basic system functionality for user applications and calls some lower-level APIs.

kernel32.dll is primarily responsible for basic operating system functions, such as file, memory, process, thread, time, and DLL management. It is one of the most important foundations for interaction between applications and the operating system kernel on Windows.

Many operations go through ntdll.dll before interacting further with the kernel.

Common API examples

  • File management:
    • CreateFileW / ReadFile / WriteFile / DeleteFileW
  • Memory management:
    • VirtualAlloc / VirtualFree / VirtualProtect
  • Process and thread control:
    • CreateProcessW / ExitProcess / CreateThread / TerminateThread
  • System time/timing:
    • GetSystemTime / Sleep
  • DLL loading/management:
    • LoadLibraryW / FreeLibrary / GetProcAddress

It can be understood that almost all Windows applications automatically load kernel32.dll when they start. Therefore, hooking ntdll.dll or kernel32.dll makes it possible to intercept most behaviors that have a significant impact on the system.

Solve DLL hook

There are several approaches. Common ones include:

  1. DLL unhook: Restore the DLL and remove the hook.
  2. Direct syscall: Bypass DLLs that may be hooked and call the syscall directly.
  3. Indirect syscall: Use a legitimate DLL execution path to call the target syscall.

Unhook

Simply put, this involves finding the location of the hook. In the case of an inline hook, this means finding the jump at the beginning that redirects execution to the EDR to determine whether the DLL has been hooked. Then, overwrite the hooked code with code from a clean DLL (from disk / Windows cache) to restore the API to its original state. At this point, even if something in the DLL is executed, the EDR will not see it.

Many techniques have been developed since then. I may add more when I have time, but this is essentially how a basic unhook works.

Direct Syscalls

Call syscalls directly, without going through a hooked DLL such as ntdll.dll to execute those important functions.

  • https://github.com/jthuraisamy/SysWhispers2
  • https://github.com/klezVirus/SysWhispers3
  • https://github.com/am0nsec/HellsGate

This requires reading addresses from the loaded ntdll.dll and dynamically calculating the syscall number and system service numbers (SSN), so the code does not need to be rewritten for every version.

However, there is still a chance of leaving traces and being detected because:

  • The syscall instruction executes outside the memory of ntdll.dll, which is unusual.
  • The return instruction does as well.

Both of these are considered non-legitimate on Windows.

Indirect Syscalls

Use the Native APIs in ntdll.dll, such as NtOpenProcess and NtWriteVirtualMemory, to make system calls without going through higher-level DLLs such as kernel32.dll.

Because execution occurs directly in the memory of ntdll.dll, and the return also occurs in ntdll.dll memory before pointing to the indirect syscall assembly that actually needs to execute, the disadvantages of direct syscalls mentioned above are resolved. However, if the EDR uses ETW (Event Tracing for Windows), it may still discover anomalies through the call stack.

However, if ntdll.dll itself has also been hooked, attempting to use ntdll.dll to perform an indirect syscall will still be visible to the EDR.
