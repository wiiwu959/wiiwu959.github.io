PACMAN: Attacking ARM Pointer Authentication with Speculative Execution

paper: https://pacmanattack.com/paper.pdf

Abstract

This paper proposes a new attack called PACMAN. It combines memory corruption vulnerabilities with speculative execution vulnerabilities, using side channels to speculatively leak the result of PAC verification without causing a crash. The attack was successfully demonstrated on the Apple M1 SoC, the first personal-computer processor to support ARM Pointer Authentication.

Introduction

PACMAN is primarily a hardware-related attack. Previous vulnerabilities such as Meltdown and Spectre were also hardware-related. PACMAN mainly targets the speculative execution feature to bypass ARM pointer authentication.

ARM Pointer Authentication

When carrying out memory-related attacks, attackers often need to control data pointers and then control the execution flow. ARM therefore provides Pointer Authentication (PA) to protect pointers from being modified. This protection makes it difficult to tamper with a pointer without being detected.

In general, the actual address space on a 64-bit architecture is smaller than 64 bits, so the unused bits can be used to store a hash value—a Pointer Authentication Code (PAC)—to protect the pointer. If the PAC is incorrect when the pointer is used, the program crashes.

A PAC can be as small as 11 bits or as large as 31 bits, depending on the system configuration. However, even a small PAC is not easy to brute-force, because after a crash and restart, a new secret key is used, and crashing too frequently is also easy to detect.

Key Challenge

The research challenges on Apple platforms were:

  • Very little public documentation exists about their microarchitecture.
  • By default, high-resolution timers are not exposed to userspace.
    • (Such timers are said to be very important for microarchitectural reverse engineering.)

Contributions

  • Propose the PACMAN attack.
  • Develop microarchitectural timing side-channel attack primitives and a reverse-engineering tool for Apple M1 processors.
  • Reverse-engineer the TLB organization and perform the first TLB-based side-channel attack using speculative execution on Apple M1 processors.
  • Show that the PACMAN attack works across privilege levels. (We demonstrate several proof-of-concept PACMAN attacks, including constructing PAC oracles, brute-forcing PACs, and a control-flow hijacking attack targeting a PA-enabled kernel module.)

Impact

  • Industry: It can affect all ARM processors that use existing PAC designs.
  • Academia: Many papers and assumptions based on memory-safety premises can be invalidated, making it necessary to modify and reevaluate the threat model.
  • Highlights that security mechanisms employing a security-by-crash design principle and relying on a low collision probability are potentially vulnerable to speculative execution attacks.
  • Speculation can serve as a primitive for suppressing crashes.

Background

Memory Corruption Vulnerabilities

These vulnerabilities occur in software written in low-level languages, including:

  • out-of-bound writes
  • out-of-bound reads
  • use-after-free
  • double-free bugs
  • integer overflows and underflows
  • size confusion attacks
  • type confusion attacks

They can modify or destroy data and code pointers in memory. Modifying a code pointer can change the program’s execution flow and cause serious consequences. This is also known as a control-flow hijacking attack; ROP and JOP are examples.

Common protections include:

  • stack canaries
  • data execution prevention
  • ASLR
  • kASLR (kernel ASLR)

Although these protections increase the difficulty of attacks, they can still potentially be bypassed.

ARM Pointer Authentication

ARMv8.3 introduced PA as a low-overhead protection mechanism to prevent pointers from being modified. It primarily protects pointers by signing them with a hash, called a Pointer Authentication Code (PAC). The PAC is checked before the pointer is used.

Signing and Verifying Pointers

In practice, a 64-bit architecture does not use the entire 64-bit address space. PA stores the PAC in the unused bits.

The context value used to generate the hash shown in the figure contains a key in a register accessible only at a higher privilege level, as well as a program-specified salt.

ISA Extension


To provide PA functionality, PA provides two groups of instruction sets for these operations:

  • Instructions beginning with pac perform signing.
    • The hardware can keep up to five keys recorded simultaneously. The key used for a particular signing operation is determined by the opcode.
    • e.g. pacia ptr, salt
  • Instructions beginning with aut perform verification.

On Apple chips, in addition to protecting return addresses, PAC is also used to protect many other data structures, including C++ vtable pointers, vtable entries, and Objective-C method caches.

Microarchitectural Side Channels

Shared microarchitectural structures, including caches, TLBs, functional units, and networks-on-chip, can be used to leak sensitive information.

Prime+Probe

  • Has relatively few restrictions.
  • The attacker first fills the cache. After the victim accesses it, the attacker accesses the entire cache again and uses timing differences to determine which parts the victim accessed.

Flush+Reload

  • Requires shared memory.
  • The attacker first flushes the memory locations to be observed. After the victim finishes executing, the attacker scans the memory again and uses timing differences to determine which locations were accessed.
  • Used by both Meltdown and Spectre.

Evict+Reload

  • Requires shared memory.
  • Similar to Prime+Probe, but operates on shared memory.

Speculative Execution Attacks

Speculative execution is a processor optimization. Because processors operate very quickly, they execute ahead in order to make better use of their resources. For example, with branch prediction, the processor guesses which path a branch will take before the branch condition is determined and begins executing that path. If the prediction is correct, execution can continue directly; if it is incorrect, the processor returns to the branch point and takes the correct path. However, this optimization has also introduced several vulnerabilities.

Meltdown

Meltdown exploits exceptions and speculative execution. Before execution stops due to an exception, the processor speculatively runs ahead to instructions that load sensitive information and then stops.

Spectre

Spectre targets conditional branches or indirect branches.

Threat Model

  • Target
    • Use a PAC oracle on a PA-enabled victim to recover the PAC and achieve a control-flow hijacking attack.
  • Attacker
    • An unprivileged userspace application.
  • Victim
    • The operating system kernel.
  • Assumptions
    1. The victim program contains an exploitable memory corruption vulnerability that allows the attacker to write arbitrary data to memory.
    2. PA is enabled and PACMAN gadgets exist.
    3. A side-channel attack can be performed (that is, a high-resolution timer is available).

The PACMAN Attack

The main idea is to use speculative execution attacks and microarchitectural side channels to leak the result of PAC verification without causing a crash.

PACMAN gadgets

Some exploitable code patterns are referred to as PACMAN gadgets. They consist of two operations:

  • verification
    Verifies the PAC. Given a pointer, it checks whether the PAC is correct. If it is correct, it outputs a valid pointer; if it is incorrect, it outputs an invalid pointer, which causes an execution error, as described in the Background section.
  • transmission
    Speculatively executes the verified output pointer. This may involve a load or store—in other words, the pointer is speculatively translated into a physical address and used. If execution succeeds, it produces an observable side effect that can be monitored through a side channel to leak relevant information. If speculative execution fails, it produces a speculative exception. Because these events occur under a mis-speculated branch, they do not cause a crash.

PACMAN gadgets are further divided into the following two types:

  • Data PACMAN Gadget (Figure 3c)
    • Caused by speculatively predicting a branch and performing data accesses.
    • AUT: pointer authentication instruction.
    • guessed_ptr: pointer provided by the attacker.
    • verified_ptr: output pointer from AUT.
    • Whether the pointer is correct can be determined by observing the difference between a load being executed and an exception occurring.
  • Instruction PACMAN Gadget (Figure 3d)
    • Caused by speculatively predicting a branch and performing instruction fetches.
    • Before AUT completes, the branch target buffer (BTB) predicts BR2. (This is common in nested-branch prediction.)
    • After AUT completes and determines that the BR2 prediction was incorrect, it eagerly squashes BR2.
    • It fetches the correct BR2, which is the result of AUT.
    • Limitations:
      • The processor must support eager squashing of nested branches. There must be a third step that squashes the pointer after AUT; only then will the pointer be used and the result of AUT can be leaked.
      • It must be possible to distinguish the side effects of fetching the verified pointer from those of the BTB prediction. In the TLB-based side channel used by this proof of concept, the BTB prediction and the verified pointer must be on different pages.

Gadget Detection

Using Ghidra’s scripting API, conditional branches in the kernel are located and the following 32 instructions are inspected. If the verified pointer is used in a transmit instruction—a memory access or a branch instruction—it is considered a PACMAN gadget.

In xnu-8019.80.24, 13,867 data PACMAN gadgets and 41,292 instruction PACMAN gadgets were found. Because only the following 32 instructions were searched, there may be even more gadgets if a larger range is examined.

An End-to-End Illustrative Example


Suppose there is a BoF that can overwrite a function pointer.

  1. Execute the program normally and train the BTB and branch predictor (cond = true).
  2. Use the BoF to modify fp, then guess the PAC until it is correct (cond = false; the branch is not actually taken, but is speculatively executed, so no crash occurs).
  3. Finally, use the guessed PAC to complete the exploit (con = true).

Attack Platform

  • Apple M1 SoC
    • The first desktop aarch64 platform supporting ARMv8.3 extensions, including PA.
    • EL0: the execution level for usermode programs.
    • EL1: the execution level for the kernel.
  • macOS and the XNU Kernel
    • OS: macOS
    • XNU Kernel
      • Has loadable kernel extensions, or kexts.
      • Used later during reverse engineering.

None of the above is open source, and there is little documentation, so reverse engineering is needed to obtain the required information. This is also one of the paper’s major contributions.

Reverse Engineering Tools

High-Resolution Timers

As mentioned earlier, side-channel attacks such as Prime+Probe require precise timing, so the researchers identified which timers in the M1 could be used.

  • CNTPCT_EL0
    • System Counter. All cores share this counter, but its frequency of 24 MHz is too low to precisely observe differences such as cache hits and misses.
  • PMCCNTR_EL0
    • ARM Cycle Count Register. Most ARM Cortex processors have performance monitoring units (PMUs) and therefore provide this counter, but the M1’s PMU is not a standard PMU, so it does not provide it.
  • PMC0
    • This counter is not mentioned in the documentation and counts cycles. There is also a PMC1 that counts instructions, but neither is accessible from userspace.
    • To use it, the researchers used the previously mentioned kext to modify a control register, PMCR0, so that PMC0 could be accessed from userspace. (This was only for reverse engineering and was not used in the attack.)

    • isb is used for control flow, but they later found that omitting it slightly increased variation while providing greater timing precision, so they ultimately removed it.

PacmanOS

Written in Rust, this is a bare-metal environment that can run on the M1. It gives the researchers complete control over the environment, including the hardware and other sources of interference, making experiments easier to conduct.

Reverse Engineering

Basic Memory Hierarchy Information

The M1 uses a big.LITTLE design.

big.LITTLE: A combination proposed by ARM that combines more powerful big cores with weaker but more power-efficient little cores. Here, the terms p-core (Performance) and e-core (Efficient) are used for big and little, respectively, although these are Intel’s naming conventions.

The M1 memory system has two levels of cache, with different sizes on different cores. The kernel uses 48-bit virtual addresses and a 16-bit PAC.

L1 Data TLB and L2 TLB

The researchers mainly studied p-core behavior because speculative behavior on p-cores is more reliable. Unlike Linux, which provides an API (taskset) to directly specify which core should execute a task, they used pthread_set_qos_class_self_np to “suggest” to the kernel which core to use. The counter they used was PMC0, which requires a kext.

The experiment used Prime+Probe to measure the TLB size. The main steps were:

  1. Load a particular address.
  2. Load N addresses to fill the TLB.
  3. Load the address from step 1 again and measure the latency.

The result was Figure (a). Each gap represents the boundary of a TLB size (L1 dTLB/L2 TLB). Although this cannot conclusively prove that the cache organization is exactly as inferred, it does reveal how to fill the TLB.

TLB conflicts and cache conflicts were measured using different methods for calculating the addresses of the N loaded addresses, producing Figure (b) (L1 cache/L2 cache/L1 dTLB/L2 TLB).

L1 Instruction TLB

  1. Fill both the L1 dTLB and the L2 TLB.
  2. Branch to a particular address.
  3. Execute N branches to fill the iTLB (called the instruction eviction set).
  4. Load the address from step 2 and measure the latency. (The reason for using a “load” to obtain data-access latency is explained below.)

The result was Figure (c). Before explaining the result, the inferred overall TLB organization is described below.

  • The user and kernel L1 iTLBs are not shared, so userspace cannot observe differences in kernel space.
  • The L1 dTLB is a non-inclusive backing store for the L1 iTLB. When the iTLB is filled, entries are also placed in the dTLB. This is why step 4 above uses a “load” to measure data-access latency.

Summary of Reverse Engineering Results

  • After filling the iTLB, the dTLB can also be filled.

  • Both PMC0 and the Multi-thread Counter can clearly distinguish between TLB hits and misses, as well as cache hits and misses.

Proof-of-Concept Attacks

PAC Oracles

In the experiment, the researchers installed a kext containing a syscall that could trigger a PACMAN gadget. They then tested a large number of pointers with correct PACs and pointers without PACs, measuring the timing with the counter they defined. They used both data accesses and instruction fetches to leak whether the PAC was correct.

  • Leaking via Data Accesses
    • Because the dTLB is shared between userspace and the kernel, it can be measured directly.
    1. Train the PACMAN gadget’s branch predictor (64 times).
    2. Reset the TLB.
    3. Prime the L1 dTLB.
    4. Trigger the PACMAN gadget by passing in the pointer containing the PAC to be tested.
    5. Probe the L1 dTLB set by re-accessing the eviction set and report the number of L1 dTLB misses.
  • Leaking via Instruction Fetches
    • The kernelspace and userspace L1 iTLBs are not shared. Therefore, userspace triggers self-conflicts in kernelspace and fills its iTLB, thereby filling the shared dTLB.
    • The preceding steps are the same as for data accesses.
    1. Use the set that filled the iTLB to attempt to fill it again.
    2. Finally, check whether it was also placed in the dTLB to determine whether a miss occurred.

Brute-Force Attack

  • Attack Speed
    • The M1 uses a 16-bit PAC.
    • It takes 2.94 minutes on average to try all possible PAC values.
    • The main time cost is the syscall used to train the predictor. This could be shortened, but it is not necessary.
  • Attack Accuracy
    • Noisy environment.
    • 90% correct PAC (45).
    • 10% no PAC value was found (5).
    • No false positives (incorrect PACs).

Jump2Win Attack

Once the PAC is available, the vulnerability can be exploited directly.

Countermeasures

  • Explore PAC-agnostic execution.
    • Modify the architecture or software to ensure that PACs are not verified and used during speculation.
    • Pause speculative execution when a memory access or branch requires a verified pointer.
      • fence/isb
      • This reduces performance.
    • Always assume that the PAC will pass during speculative execution.
      • Speculatively executing with invalid pointers may cause a Meltdown-style vulnerability.
      • This must be combined with Meltdown mitigations.
  • Improve Spectre defenses.
    • Make speculative loads unobservable.
      • Invisible speculation mechanisms.
      • Such as InvisiSpec, SafeSpec, and Delay-on-Miss.
    • Use information-flow tracking to prevent secrets accessed speculatively from being leaked.
      • STT, NDA, and Dolma.
      • Taint pointer authentication instructions.
  • Do not write programs containing memory corruption vulnerabilities.
