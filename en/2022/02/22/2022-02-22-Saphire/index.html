Saphire: Sandboxing PHP Applications with Tailored System Call Allowlists

paper: https://www.usenix.org/system/files/sec21-bulekov.pdf

Abstract

  • PHP and Python are interpreted languages. Applications written in these languages often run with the same excessive privileges, violating the Principle of Least Privilege (PoLP)—that is, the principle that fewer privileges are better. This exposes the entire system to danger: once an RCE occurs, it is easy for an attacker to obtain overly high privileges and expose the system to even greater risks.
  • This paper aims to implement PoLP by properly controlling privileges, using the authors’ proposed method of automatically generating a syscall policy for each individual program.

Background

  • RCE
  • seccomp
    • Specifies that a process may call only particular system calls
  • ptrace
    • Allows a tracing process to observe or control the contents (such as memory or registers) or execution flow of another traced process
    • Primarily used to implement debuggers or trace syscalls

Overview

Interpreters

  • Interpreted program: a program that requires an interpreter to execute
  • An interpreter can be directly executed by the OS and hardware

Therefore, interpreted programs are portable. An interpreted program typically provides users with an API composed of several functions, and only these APIs can access syscalls. Even when JIT is used, syscalls can still be called only through the API.

An API for all interpreted programs

Because these APIs generally need to be highly general-purpose, they usually use many syscalls at once, so simply filtering syscalls is not meaningful. However, a program may use only a small subset of syscalls, in which case filtering can be useful.

For example, Prog1 does not need syscall1, so it can be filtered out.

Securing Interpreted Programs

  • Mapping the interpreter API to syscalls
    Use static and dynamic analysis to map API function handlers to syscalls
  • Identifying API calls within an interpreted program
    Identify the functions used in each piece of code, including all dependencies (both implicit and explicit), and then use the preceding mapping results to generate an allowed list
  • Protecting the Program
    Apply the allowed list to the program

Implementation

The steps mentioned above are implemented and explained using PHP here.

Mapping built-in PHP functions to system-calls

Map PHP functions to the system calls they use.

  • First, use static call-graph analysis to perform an initial mapping.
  • Then, use ptrace to observe the syscalls used while running the PHP process.

Static analysis over the PHP Interpreter

  • Use symbols to construct the static call graph of the entire interpreter and libraries (each node is a function, and each edge is a direct function call).
  • To find all handlers, use get_defined_functions() to locate the addresses of all built-in PHP function handlers.

Although this step is static, it must be run across many code bases (after examining the code, the paper also states that this takes more than 30 minutes).

Refining the mapping through dynamic analysis

Although the previous step exhaustively scanned the code in the entire PHP process, it misses indirect calls. For example, PHP’s fopen can access remote files, and some functions such as mail() execute the sendmail binary. Purely static analysis cannot map the syscalls invoked by sendmail.

  • TE finds the name of the PHP function currently running in shared memory.
  • TR uses ptrace to intercept syscalls.

Combining these two makes it possible to dynamically map this kind of function.

Creating system-call filters for web apps

The purpose of this step is to identify which PHP built-in functions the interpreter will invoke, and then compare them with the mapping table generated in the previous step to generate the system calls that each script in the web app may call.

  • First, iterate through all PHP files in the web app.
    • Use php-parser to generate an Abstract syntax tree (AST).
    • Scan the AST to identify possible built-in function calls.
    • Check assignments to determine class types and thereby map the functions.
  • Identify dependencies in the AST.
    • constant definitions
    • class definitions/instantiations
    • include/require operations

The most labor-intensive part is handling dependencies. Simple includes can be handled easily, but if variables or constants are used, additional processing is required.

String representation

Various methods are used to convert include strings of different kinds until they can no longer be processed or processing is complete.

(If a variable is assigned multiple times, each assignment is identified; if this is not possible, all possibilities are listed.)

Unresolved Includes

At this point, 74% of includes can be resolved. The remainder can be fuzzy resolved, meaning that a small set of contents is treated as having been included.

Some includes provide no information at all through static analysis. In this case, they provide a Conservative Includes option, which uses this method. After enabling this option, the probability of FP decreases, but the contents of the allowed list become more extensive.

Building system-call profiles for Scripts

Finally, once we have a script, the PHP functions that it and its dependencies will call, and the mapping obtained in the previous step, we can generate a profile mapping the script to its syscalls (script path <-> profile).

Sandboxing the Interpreter and Web App

This allowed list is implemented using seccomp. This SE extension determines which script the process is running when it starts and tells the kernel which syscall allowed list to use.

Therefore, this SE runs twice during the lifetime of an interpreter. The first time is when the PHP process starts, when all allowed lists are loaded into memory. When a request is received, the applicable allowed list is sent to the kernel.

(libseccomp is used to convert a sequence of syscalls into an allowlist.)

  • Web requests are usually handled by a web server such as nginx or Apache, so this plugin is installed on the web server as well as in the PHP CLI API (the command-line interface).
  • Because seccomp is used, a process can run only one script (a process cannot suddenly switch to a different allowed list).
    • A PHP interpreter process can be used for only one request, but this approach results in very high latency when loading is expensive.
    • Each PHP worker can handle many requests, but the same worker can handle requests for only the same script.

Evaluation

Dependency Resolution

  • All dependencies are divided into those that can be resolved literally and those that require dynamic resolution.
  • Resolved avg -> 74%
  • Fuzzy resolved -> 22%
  • Class 85%
  • For example, Joolma changes many original classes to call them using aliases, which cannot be detected in this case.

Syscall Profile Size

  • To understand how many syscalls are filtered and how effective CI is, examine the size of the syscall profile. The larger the size, the more syscalls are available, so it should be kept as small as possible while still allowing the program to run.
  • Dangerous syscalls were also evaluated in particular.
  • The black line represents the state when CI is not enabled.
    • When it is enabled, FP decreases, but the danger increases.
  • Approximately 80% of dangerous system calls are filtered.
  • Some common functions appear in many scripts, making the profiles of many scripts very similar.

Defense Capabilities

  • 21 RCE exploits were selected for testing.
  • Is too restrictive?
    • Calculate coverage to demonstrate that the program executes normally.
    • After enabling CI, there is no FP at all.
    • After disabling it:
      • Joomla is affected by the alias issue mentioned above.
  • Payload constraint?
    • The dangerous syscalls remaining after filtering are insufficient to construct a payload capable of ACE. They also performed many additional tests and found that the remaining syscalls lacked the components needed to assemble a payload.
  • Non-vuln plugins
    • Non-vulnerable plugins were also tested to evaluate FP.
  • Runtime Overhead
    • The key issue arises after implementation in the web app. Because of the seccomp issue mentioned above, the process must be restarted after each request is processed.
    • The resulting overhead is small enough to be negligible. Even particularly trivial scripts are not affected significantly. In particular, after implementing the method whereby “the same worker can handle requests for only the same script,” the impact is even smaller.

Limitations and Discussion

  • eval() system()
    • They do not handle these two functions or their arguments.
  • Mimicry
    • Although the results are already very good and no RCE occurred in the tests, some dangerous syscalls are still allowed and may be combined into a payload.
  • Overwriting scripts
    • If an attacker can modify a script and mislead the profile, this can be addressed simply by using a checksum.
  • Writing to sensitive files
    • To prevent attackers from gaining privileges by writing files, ptrace is also used to ensure that the interpreter cannot access certain important fds (file descriptors).
  • Installing plugins
    • When a new plugin is installed, a profile is immediately created for it, but this requires manual action.
  • Filter system call argument
    • In addition to directly filtering syscalls, filtering their arguments as well would provide greater precision.
  • Line coverage of evaluated web apps
  • Applying Saphire to other interpreters
    • Python interpreter running a program composed of multiple python scripts
    • A server executing multiple Node.JS microservices
    • classic CGI-based interpreted web-app using a language such as Perl or Lua
