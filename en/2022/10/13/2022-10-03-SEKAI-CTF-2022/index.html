SEKAI CTF 2022 writeup

This is my first time writing a writeup as a blog post. The interface for this competition was really cute, and as a Project Sekai player, I felt that I had to participate somehow. I also happened to encounter a challenge that I found quite interesting. At first, I thought it would be unlikely that I could solve it during the competition, but I luckily managed to solve it later. I ended up solving two easy challenges in total, so I am recording them here. The challenges are still available; I will add more if there are any updates.

Bottle Poem

http://bottle-poem.ctf.sekai.team 146/852 solve

The page for this challenge looks like this. There are several links in the middle of the page. Clicking a link takes you to a URL like http://bottle-poem.ctf.sekai.team/show?id=spring.txt, which retrieves the corresponding poem’s txt file and displays it on the page.

The /show?id= endpoint looked like it might allow file reading, and using id=/etc/passwd did indeed retrieve the file. After looking around, I found that:

  • If the file does not exist, it displays No This Poems.
  • id=/proc/self/cmdline displays python3.
  • id=../app.py displays No!!!!

At this point, I could infer that it was probably running on a Python web framework similar to Flask, so I wanted to see whether I could retrieve some source code that Flask might have. Although using ../app.py returned No!!!!, using id=/app/app.py could actually retrieve the source.

Now it was clear why ../app.py returned No!!!!. At this point, I wondered whether I needed to log in as admin. Logging in as admin was actually quite simple, because it only checked the value of "name" in the cookie. I just needed to retrieve the secret with id=/app/config/secret.py and sign a cookie satisfying session["name"] == "admin". However, things were of course not that simple: visiting the /sign page with the admin cookie only produced a page like this.

Before trying this, I could already have realized that it was a dead end by using id=/app/views/admin.html (although it did not take much effort). While wondering what this challenge actually wanted us to do, I remembered that the format of this cookie looked somewhat like JSON. Could it have something to do with unserialize again? After searching for a while, I found Python Web Framework Session Management: From LFR to RCE (I found a translation, but I could not find the original article… I will add it if I find it). It happened to discuss the Bottle framework. After looking through the source, I saw that its get_cookie function uses pickle.loads to process this cookie! The answer was then obvious: use unpickle RCE.

Finally, I made a simple script based on the source to generate the cookie and prepared to receive a reverse shell. This challenge required executing a file in the root directory to print the flag, so that was it.

Sekai Game Start

http://sekai-game-start.ctf.sekai.team 63/852 solve

This was a PHP challenge that directly showed us the source code. In short, we needed to send it a serialized string. Clearly, it had to be a serialized string for Sekai_Game, and when Sekai_Game reached __destruct, $start had to be true in order to obtain the flag.

There were two key points in this challenge:

  • How to send the "sekai_game.run" parameter.
  • How to bypass the __wakeup function.

The first point was a problem because when passing GET parameters to PHP, . is automatically converted into an underscore. No matter how it was sent, it was therefore impossible to provide the parameter correctly. This parameter was arguably not a particularly valid one either. However, after looking into the source code for this version (php 7.4.5), I found a section in main/php_variables.c that performs these conversions. I then discovered that when PHP encounters the character [, it treats it as an array and performs the subsequent array-related checks. However, if it cannot find a closing ], it converts the [ into _ and stops. Most importantly, it does nothing else, including checking the characters that follow. Therefore, when we send sekai[game.run, it is ultimately converted into the sekai_game.run we need.

HexRabbit initially looked at the wrong version. This part had already been fixed, so they could not find this solution for a long time, but they did learn that it had later been changed XD

The second problem was how to bypass __wakeup. For Sekai_Game‘s start to be true, execution must not enter __wakeup. I found PHP Bug #81151 bypass __wakeup, where the object used "C" rather than "O" in the serialized string. In the bug report, the author said:

In my understand, “C:” means a class implements Serializable, and it don’t suport __wakeup.

I am not sure whether this is correct, and the author was not sure either, but constructing the payload this way did work (it does not work on php8). Thus, the final solution was:

I do not understand it either, but that is how it worked. This challenge was a double dose of obscure tricks. When I could not solve it, I felt completely stuck, because I was fairly sure it must be testing some kind of obscure trick XD. However, I really wanted to know the solution and could not wait until the competition ended, so I asked people about it everywhere. Fortunately, I still managed to solve it myself before the end. After solving these two challenges, though, I did not have much energy left to look at the others. My patience and stamina are really limited, but I hope I can continue improving little by little.
